# AGENTS.md

## Layout
- Backend entry: `app.main:app` (FastAPI). Routes: `app/routes/auth.py` (`/api/v1/auth/*`), `app/routes/chat.py` (`/api/v1/chat`, `/chat/stream`, `/chat/sse`). RAG core: `phase1.py` (`RAGSystem`). Eval: `eval_cases.json`, `langsmith_eval.py`.
- Frontend: `frontend/` (Vite + React). SSE client: `frontend/src/api/chatApi.js`. Vite proxies `/api`, `/health`, `/ready` — keep same-origin.

## Backend startup (order matters)
- Lifespan in `app/main.py`: validate `JWTService.from_environment()` first → `ping` Redis → `ping` Mongo → init Chroma RAG (ingests `data/*.txt` if `learning_rag` empty) → sets `app.state.ready`.
- `/health` is liveness (always 200). `/ready` is 503 until Chroma has docs.
- Chroma path: `chroma_data/`, falls back to `runtime_chroma_data/` if primary isn't writable. Both are gitignored; never commit them.
- `phase1.py` lazily creates the Gemini client — importing it needs no credentials/network. Don't move client construction to import time.

## Auth contract (don't redesign)
- Access JWT 15 min (Bearer, in-memory only). Refresh JWT 7 days, HttpOnly cookie `refresh_token`, `Path=/api/v1/auth`, `SameSite=Strict`, `Secure=true` by default.
- Redis holds sessions as `auth:refresh:<jti> -> user_id` with `EXAT=<jwt exp>` + `NX`; rotation is single `GETDEL`; logout is `DELETE`. Command retries are deliberately disabled (repeating `GETDEL` after a lost reply is unsafe). Never trust a refresh JWT without its Redis entry; never put refresh tokens in localStorage.
- Chat authorization (`app/dependencies/chat.py`): `payload.user_id` must equal JWT `sub`, else 403. A 401 means re-login; a 503 means infra failure (retry, don't treat as bad credentials). Logout of an already-invalid cookie still returns 204 + clears cookie.
- `AuthRoute` strips request bodies from 422s and sets `Cache-Control: no-store` / `Pragma: no-cache` on all auth responses — preserve both.

## RAG invariants
- Retrieval is always filtered by `where={"user_id": ...}`; chunk ids are `{user_id}:{doc_id}:{index}`. Never drop the filter.
- Unanswerable → return exactly `I do not have enough information to answer that.` History is for reference resolution only, never a factual source.
- Limits enforced at both schema and `RAGSystem.retrieve`: `k` 1–10, `raw_query` 1–4000 chars, `chat_history` ≤20 msgs (last 8 used), message content ≤8000, `distance_threshold` 0–2 (cosine). Defaults: chunk 512/64, models `gemini-embedding-2` / `gemini-3.6-flash`.
- `load_txt_documents` normalizes the `embeedings` filename typo to doc id `embeddings` (matches `eval_cases.json`) — don't "fix" by renaming the effect.
- SSE event order: `start → retrieval → token* → sources → done`, or `error` (with `stage` + generic message). Frontend validates these strictly.
- Long-conversation summarization (Phase 1): past `SUMMARY_THRESHOLD` (default 20) completed messages, RAG gets one leading `system` summary message + last 8 verbatim (`SUMMARY_KEEP_RECENT`) instead of raw 20. Summary stored on `conversations` (`summary`, `summary_message_count`, `summary_updated_at`), refreshed after `SUMMARY_MAX_AGE` (default 10) new messages. LLM call lives in `phase1.summarize_conversation_history`; service layer never prompts. Orchestration seam for tests: `chat_orchestration.default_summarize_fn`.
- Hybrid retrieval (Phase 2, flag-gated default-off via `HYBRID_ENABLED`): `app/services/retrieval.py:HybridRetriever` builds a per-user in-memory BM25 index (`rank_bm25`, lazy import) from `collection.get(where={"user_id": ...})`, over-fetches `min(10, max(2*k, HYBRID_OVERFETCH_MIN=20))` per leg, fuses with RRF `1/(HYBRID_RRF_K=60+rank)`. `RAGService` owns the long-lived cache and invalidates on ingest/delete; `RAGSystem._retrieve_chunks` falls back to vector-only on any BM25 failure. Per-request override: `use_hybrid=True/False/None(env)` on `run_once*` / `hybrid_retrieve`.
- Reranking (Phase 3a, flag-gated default-off via `RERANKER_ENABLED`): `app/services/reranker.py:CrossEncoderReranker` (default `cross-encoder/ms-marco-MiniLM-L-6-v2`, `sentence-transformers`, lazy import on first use — never at startup) rescores the over-fetched candidate window (up to 10 chunks) and keeps `min(k, RERANKER_TOP_K=5)`. Runs in `RAGSystem._retrieve_chunks` after hybrid/vector fetch; any failure keeps retrieval order. Per-request override: `use_rerank=True/False/None(env)` on `run_once*`. Cross-encoder only — no Cohere backend yet.
- JWT blacklisting (Phase 4, always on): `app/services/token_blacklist_service.py:TokenBlacklistService` stores revoked access JTIs as `auth:blacklist:<jti> -> 1` with `EXAT=<jwt exp>` + `NX` (auto-expire, no cleanup). `get_current_user` rejects listed tokens with 401 and maps Redis outage to 503 (fail-closed). Logout/refresh accept an optional Bearer access token and blacklist its JTI (absent/undecodable tokens ignored, contracts unchanged: logout still 204, refresh still 401-on-bad-session).
- Response caching (Phase 5, flag-gated default-off via `CACHE_ENABLED`): `app/services/cache_service.py:CacheService` stores answered payloads as `response_cache:<user>:<gen>:<sha256(user, query, sorted chunk ids)>` with `EX=CACHE_TTL_SECONDS` (default 3600). Lookup sits in `RAGSystem.run_once*` after retrieval, before the LLM call; hits replay the stored answer through the unchanged event/result shape. Only successful grounded answers are stored (errors propagate, refusals/empties skipped). Invalidation is a per-user generation bump (`response_cache:gen:<user>` via `INCR`) called by `RAGService` on ingest/delete — O(1), orphans expire via TTL. Fail-open (never raises into chat): Redis trouble means uncached answers. Per-request override: `use_cache=True/False/None(env)` on `run_once*` / `RAGService.run_once*` / `chat_orchestration.run_chat_once`. When consulted, `run_once` adds `cache_hit` and SSE `done` carries `{"metadata": {"cache": "hit"|"miss"}}`; uncached callers keep byte-identical outputs (`done` stays `{}`).
- Production retries (Phase 6, always on): `app/utils/retry.py:retry_with_backoff` retries transient failures only (timeout, connection errors, 429/5xx via duck-typed `code`/`status_code` — never other 4xx, auth/duplicate-key errors, bugs, or cancellations) with exponential backoff + jitter (`RETRY_MAX_ATTEMPTS=3`, `RETRY_BASE_DELAY=0.5`, `RETRY_MAX_DELAY=8.0`, resolved per call). Applied to all Gemini calls in `phase1.py` (`circuit="gemini"`) and all Mongo service methods (`circuit="mongodb"`, except the delegating `get_summary_state` to avoid nested-retry amplification). Service domain exceptions (`raise StoreUnavailable from error`) are seen through via the `__cause__` chain. Generators retry only before the first yielded item (never mid-stream, to avoid duplicate output). `CircuitBreaker` opens after `CIRCUIT_BREAKER_THRESHOLD=5` consecutive transient failures and fails fast for `CIRCUIT_BREAKER_COOLDOWN_SECONDS=30`, then half-open probes; thread-safe, shared per dependency name (`get_breaker` / `reset_breakers` test seam). Retried inserts use fresh backend uuids per attempt (at-least-once tradeoff, documented in the module).
- Degraded LLM responses (Phase 7, flag-gated default-off via `DEGRADED_MODE_ENABLED`): when the LLM is unavailable after Phase 6 retries (transient error exhausted, or open `gemini` circuit — never bugs/4xx, never empty retrieval which keeps the refusal), `RAGSystem.run_once*` serve the top `DEGRADED_MAX_CHUNKS=3` chunks as plain-text excerpts under the exact `I'm experiencing high load...` prefix. Pre-stream failures degrade; mid-stream failures keep the `error` event (a partial answer must not be replaced). Degraded answers are never cached (the LLM may have recovered), are counted in Redis (`llm:degraded:responses` via `app/services/degradation_service.py:DegradationTracker`, fail-open), and surface as `run_once["degraded"]` / SSE `done.metadata.degraded` / a `ChatWindow.jsx` banner (`.degraded-note`). Per-request override: `use_degraded=True/False/None(env)` on `run_once*` / `RAGService.run_once*` / `chat_orchestration.run_chat_once`.
- Token/cost monitoring (Phase 8, always on): `phase1` captures Gemini `usage_metadata` (`prompt_token_count` / `candidates_token_count` / `total_token_count`, strict ints only so Mock attributes never fabricate rows) into a caller-owned `usage` collector on `generate_answer` (direct) and `generate_answer_stream` (last-chunk-wins on clean completion). `run_once` attaches `result["usage"]`, SSE `done` carries `metadata.usage`, plain-text streams fill the route-owned collector; absent/invalid metadata keeps byte-identical outputs. `chat_orchestration` records rows fail-open (a ledger outage is logged, the answer still goes out) via `app/services/usage_service.py:UsageService` into MongoDB `usage_logs` (`usage_id`, `user_id`, `timestamp`, token counts, `model`, `cost_usd` estimated at `COST_PER_1K_INPUT=0.0001` / `COST_PER_1K_OUTPUT=0.0004` per 1K). `GET /api/v1/usage?days=7` (`app/routes/usage.py`, auth-scoped, 503 without service) returns UTC-calendar daily groups plus rolled-up totals. Only generation calls are metered (rewrite/summary calls carry no user context, excluded by design).
- Agent loop (Phase 11, flag-gated default-off via `AGENT_ENABLED`): `app/agents/` routes each query (`nodes.decide_route`: smalltalk → `direct` answer with no retrieval/LLM, everything else → `retrieve`) then runs retrieve → generate → check_confidence → respond_or_retry. Retrieval reuses `RAGSystem._retrieve_chunks` (tenant filter + hybrid RRF + rerank unchanged); confidence is `1 - mean_distance/2` (refusal/empty/no-chunks → 0.0, direct answers → 1.0); weak answers retry with a wider `k` window up to `AGENT_MAX_ITERATIONS=3`, then the best-effort answer (or refusal) is returned with `gave_up=true`. `langgraph==1.2.11` (`StateGraph`, lazy import in `graph.build_graph` — never at startup) is preferred, with an identical dependency-free manual loop on import/compile failure. Terminal generation failure honors the Phase 7 degraded-excerpt path when enabled. `RAGService.run_once` owns the fail-open integration (agent exception → legacy `rag.run_once`); streams keep the legacy path. Per-request override: `use_agent=True/False/None(env)` on `RAGService.run_once` / `chat_orchestration.run_chat_once`. Results are `run_once`-shaped plus additive `result["agent"]={route, attempts, confidence, gave_up, tools_used}` (ignored by `ChatResponse`). Best-attempt tracking: `nodes.track_best` keeps the highest-confidence attempt, so retries strictly improve (final answer/chunks/usage come from the winner).
- Agent tools (Phase 12, no new dependencies — stdlib only): `app/tools/` holds `BaseTool` (`name`/`description`/`match`/`execute`), `CalculatorTool` (safe `ast` evaluation, never `eval`: `+ - * / // % **` + parens + `sqrt/log/sin/cos/...` + `pi/e/tau`; errors → `{"ok": False}` dicts), `WebSearchTool` (`SEARCH_BACKEND=tavily|serpapi|none` via `TAVILY_API_KEY`/`SERPAPI_API_KEY`, top `SEARCH_MAX_RESULTS=5` as `{title, snippet, url}`, `SEARCH_TIMEOUT_SECONDS=10`; unconfigured/failing backends → error dicts, never raise), and `ToolRegistry` (`register/get/all/describe/select`, calculator-first order; `resolve_registry(None|registry|list)`). Agent flow gains a `use_tools` node after routing: calculator answers math directly (`"The result of …"`, confidence 1.0, no retrieval/LLM); web results become grounding chunks (`document_id="web_search"`, distance 0.5) for generation; tool misses/failures/empty results fall through to local retrieval; retries always use the corpus. `run_agent(tools=...)` overrides the default registry (empty list disables tools); custom tools just subclass `BaseTool`.

## Env (PowerShell repo — use `; if ($?) {}` not `&&`)
- `.env.example` (root) holds **additions only** (`REDIS_URL`, `REFRESH_COOKIE_SECURE`) — merge into existing `.env`, never replace it. Required existing keys: `JWT_SECRET_KEY` (≥32 UTF-8 bytes, HS256), `JWT_ISSUER`, `JWT_AUDIENCE`, MongoDB/model + Gemini keys. Never print or hardcode secrets.
- Local dev only: `$env:REFRESH_COOKIE_SECURE='false'` (HTTP). Leave `true` in production.
- Frontend `frontend/.env.example` has only `API_PROXY_TARGET` (default `http://127.0.0.1:8000`). Never put Gemini keys in browser env vars.
- Needs Redis server 7.2+ (uses `GETDEL`, `SET ... EXAT ... NX`); installing `redis==8.1.0` client does not start a server.

## Frontend gotchas
- Refresh at most once per 401 and only before an SSE stream starts; serialize concurrent refreshes (loser gets 401 + cleared cookie, so last-writer can clobber the winner). Never auto-refresh on 403, never replay a partial stream, never blindly retry side-effecting ops. No auto refresh/retry implementation exists yet — see `PHASE_3_4_AUTH.md` for the intended flow.
